# راهنمای توسعه و نگهداری

این راهنما زیرساخت توسعهٔ فاز اول و فرمان‌های جاری را توضیح می‌دهد. عملیات ایجاد پرسنل، اتصال حساب و ارتقای محدودیت‌های Member در [راهنمای فاز سوم](personnel.fa.md) آمده است. اجرای عمومی یا استقرار تولید در محدودهٔ این فاز نیست. دستورات را از ریشهٔ مخزن اجرا کنید.

## پیش‌نیاز و اجرای نخست

Docker به همراه Compose، پایتون ۳ و Bash لازم است. پورت‌های محلی ۸۰۸۱ تا ۸۰۸۴ باید آزاد باشند. نصب PHP، Composer و Node روی میزبان برای اجرای داکری لازم نیست.

```bash
./scripts/dev up
```

در یک checkout تازه، این فرمان تنظیمات خصوصی را می‌سازد، imageها را آماده می‌کند، سرویس‌ها را بالا می‌آورد، migrationها را اجرا می‌کند و پس از آماده‌شدن سرویس‌ها، هر دو منبع ورود و کاربران فعال آن‌ها را ثبت و ایمپورت می‌کند. ساخت اولیه ممکن است چند دقیقه زمان ببرد.

اگر `.env` وجود نداشته باشد، bootstrap آن را با رمزهای تصادفی تولید می‌کند. اگر قبلاً این فایل را دستی ساخته‌اید، متغیرهای الزامی آن باید مقدار معتبر داشته باشند؛ کپی‌کردن نمونهٔ خالی به‌تنهایی کافی نیست. فایل `.env` و پوشهٔ `.runtime/` خصوصی و خارج از Git هستند. رمزها را در راهنما، کد یا خروجی اشتراکی قرار ندهید.

## آدرس‌ها و حساب‌ها

| خدمت | آدرس |
| --- | --- |
| سامانه | http://localhost:8081/ |
| pgAdmin | http://localhost:8082/ |
| مدیریت Keycloak اصلی | http://localhost:8083/auth/admin/ |
| مدیریت Keycloak سازمان همکار | http://localhost:8083/identity/secondary/admin/ |
| مدیریت Camunda | http://localhost:8084/ |

برای آزمایش ورود به سامانه، نام کاربری از `DEMO_USERNAME` و گذرواژه از `DEMO_PASSWORD` در `.env` خوانده می‌شود. مقدار پیش‌فرض نام کاربری `demo` است؛ رمز ثابت و عمومی وجود ندارد. نام و رمز مدیر Keycloak اصلی در `KEYCLOAK_ADMIN` و `KEYCLOAK_ADMIN_PASSWORD`، رمز مدیر منبع دوم در `SECONDARY_KEYCLOAK_ADMIN_PASSWORD` و اطلاعات pgAdmin در `PGADMIN_EMAIL` و `PGADMIN_PASSWORD` هستند. مقادیر را در ویرایشگر خود ببینید.

realm توسعه در هر دو Keycloak، `organization-dev` است. Camunda از حساب آزمایشی و منبع اصلی استفاده می‌کند. ورود عادی سامانه و callbackها از همان پورت ۸۰۸۱ عبور می‌کنند؛ پورت ۸۰۸۳ برای مدیریت است.

## کار روزمره

```bash
./scripts/dev status
./scripts/dev logs backend frontend
./scripts/dev restart
./scripts/dev down
./scripts/dev up
```

`down` سرویس‌ها و شبکه را متوقف/حذف می‌کند و volumeهای داده را نگه می‌دارد. `up` معمولی اطلاعات دیتابیس‌های موجود را پاک نمی‌کند. فایل‌های backend و frontend به کانتینرها متصل‌اند؛ در صورت مشکل تشخیص تغییرات فرانت، `WATCH_POLLING=true` را در `.env` قرار دهید و `./scripts/dev up` را دوباره اجرا کنید.

پس از تغییر وابستگی‌ها یا تنظیمات runtime، `up` را اجرا کنید تا image، وابستگی‌ها و کانتینرها همگام شوند. آدرس پشتیبانی‌شدهٔ این فاز `http://localhost:8081` است؛ bootstrap تغییر خودسرانهٔ `APP_URL` را نمی‌پذیرد، چون تنظیمات کلاینت هویت و proxy باید با آن هماهنگ باشند.

## ثبت و ایمپورت منابع ورود

منابع توسعه `primary` و `secondary` هستند. فایل‌های خصوصی زیر با bootstrap ساخته می‌شوند:

```text
.runtime/sources/primary.json
.runtime/sources/secondary.json
```

در backend، این پوشه فقط‌خواندنی و با مسیر `/run/organization/sources/` در دسترس است. تنظیمات منبع اصلی را می‌توان بدون بازسازی realm ثبت کرد:

```bash
docker compose exec -T backend php artisan login:sources:upsert --config-file=/run/organization/sources/primary.json
docker compose exec -T backend php artisan login:import-members --source=primary --building-area=AREA_ID --dry-run
docker compose exec -T backend php artisan login:import-members --source=primary --building-area=AREA_ID
```

برای منبع دوم، `secondary` را جایگزین کنید. مقدار `--source` همیشه slug است؛ شناسهٔ عددی دیتابیس ورودی این فرمان نیست. در جدول `members` رابطه با `user_source_id` ذخیره می‌شود و ترکیب `(uuid, user_source_id)` و ترکیب `(user_id, user_source_id)` هر دو یونیک‌اند؛ یک فرد از هر منبع فقط یک حساب دارد و هر حساب خارجی به یک فرد متصل می‌شود.

کاربران فعال انسانی ایمپورت می‌شوند. کاربران غیرفعال و حساب‌های سرویس کنار گذاشته می‌شوند. اجرای مجدد رکورد تکراری نمی‌سازد و نام یا اتصال User موجود را عوض نمی‌کند. `dry-run` چیزی در دیتابیس برنامه نمی‌نویسد. اگر ایمپورت در میانه متوقف شود، رکوردهای تکمیل‌شده حفظ می‌شوند و می‌توان پس از رفع علت، فرمان را دوباره اجرا کرد. تعارض حساب اشغال‌شده یا نگاشت چند حساب یک منبع به یک فرد، در اجرای واقعی و dry-run رد می‌شود؛ هیچ اتصال موجودی خودکار جایگزین نمی‌شود.

برای اتصال صریح یک حساب خارجی جدید به User موجود، در فایل خصوصی مثلاً `.runtime/member-map.json` نگاشت شناسهٔ خارجی به شناسهٔ User را قرار دهید:

```json
{"external-subject": 123}
```

سپس اجرا کنید:

```bash
docker compose exec -T backend php artisan login:import-members --source=primary --building-area=AREA_ID --mapping-file=/run/organization/member-map.json
```

User با شناسهٔ ۱۲۳ باید موجود باشد. این نگاشت اتصال قبلی یک Member را خودکار جابه‌جا نمی‌کند. حساب‌های هم‌نام یا دارای ایمیل مشابه بین منابع، خودکار یکی نمی‌شوند.

برای منبع جدید، یک فایل JSON خصوصی زیر `.runtime/sources/` بسازید و قالب [تنظیمات و محدودیت‌ها](../technical/database.md) را رعایت کنید. callback باید دقیقاً `/login/callback/{slug}` و مقصد بازگشت خروج `/login/logged-out` روی آدرس سامانه باشد. در این فاز دو منبع داکری با مسیرهای عمومی هم‌مبدأ آماده شده‌اند؛ افزودن یک ارائه‌دهندهٔ بیرونی نیازمند هماهنگ‌کردن مسیر عمومی آن با طرح درگاه است.

تغییر تنظیمات مؤثر بر احراز هویت یا غیرفعال‌کردن منبع و اجرای `login:sources:upsert` توکن‌های قبلی آن منبع را باطل می‌کند. اسکریپت bootstrap فایل‌های دو منبع توسعه را از `.env` بازتولید می‌کند؛ برای منابع سفارشی فایل جداگانه نگه دارید.

## تنظیم کلاینت‌های توسعه

`up` این دو فرمان را نیز اجرا می‌کند:

```bash
python3 scripts/configure-identity.py --source primary
python3 scripts/configure-identity.py --source secondary
```

این اسکریپت کلاینت برنامه، callback، خروج دوطرفه، PKCE، scope استاندارد `basic` و audience لازم برای introspection را هماهنگ می‌کند و کلاینت جداگانهٔ ایمپورت را با مجوزهای خواندن کاربران می‌سازد. برای ورود برنامه، رمز مدیر Keycloak استفاده نمی‌شود؛ استفاده از مدیر در این اسکریپت فقط برای آماده‌سازی محیط توسعه است. رمزهای bootstrap باید با حساب‌های فعلی سرویس هماهنگ بمانند؛ تغییر متن `.env` به‌تنهایی رمز ذخیره‌شدهٔ یک سرویس موجود را عوض نمی‌کند.

## migration و تست

`backend-init` در `up`، migrationهای جدید را اعمال می‌کند. اجرای مستقل:

```bash
docker compose exec -T backend php artisan migrate --force --no-interaction
```

مهاجرت اصلاح رابطهٔ Member، slugهای موجود را به ID تبدیل می‌کند و داده را نگه می‌دارد. rollback باید با نسخهٔ متناظر کد هماهنگ باشد. برای رفع خطا، جدول‌ها یا volumeهای واقعی را reset نکنید.

```bash
./scripts/dev test
docker compose exec -T frontend npm run typecheck
docker compose exec -T frontend npm run build
```

تست backend از `organization_test` استفاده می‌کند. تست کامل همچنین ورود و خروج حساب‌های آزمایشی و اجرای یک فرآیند موقت Camunda را بررسی می‌کند؛ نشست حساب‌های آزمایشی ممکن است بسته شود. [نتایج واقعی بررسی‌ها](../technical/validation.md) جدا ثبت شده‌اند.

دو بررسی اختیاری زیر موقتاً سرویس‌ها را قطع می‌کنند؛ هنگام کار دیگران اجرا نکنید:

```bash
python3 scripts/smoke-provider-recovery.py
./scripts/check-fresh-development.sh
```

اولی Keycloak اصلی را متوقف و در مسیر بازیابی دوباره بالا می‌آورد. دومی پروژهٔ فعلی را متوقف می‌کند، با volumeهای موقتِ پروژه‌ای جدا راه‌اندازی از صفر را می‌سنجد، فقط داده‌های موقت همان پروژه را حذف می‌کند و محیط اصلی را برمی‌گرداند.

## نگهداری داده و عیب‌یابی

داده‌های PostgreSQL، Redis، pgAdmin و Camunda در volume نگهداری می‌شوند. قبل از جابه‌جایی یا تغییر مخرب، از دیتابیس‌های مربوط نسخهٔ پشتیبان تهیه کنید؛ محیط فعلی برنامهٔ پشتیبان‌گیری خودکار تولید نیست.

| نشانه | بررسی پیشنهادی |
| --- | --- |
| سرویس سالم نمی‌شود | `./scripts/dev status` و log همان سرویس را بررسی کنید؛ اجرای نخست ممکن است زمان بخواهد. |
| حساب در Keycloak معتبر است ولی سامانه اجازه نمی‌دهد | فعال‌بودن منبع، ایمپورت Member و تطابق UUID همان منبع را بررسی کنید. |
| بررسی حساب در دسترس نیست | سلامت Keycloak، آدرس داخلی، راز کلاینت، `basic` و audience را بررسی کنید؛ قطع ارائه‌دهنده با خروج عادی یکی نیست. |
| خروج از سرویس هویت در سامانه تشخیص داده نمی‌شود | URL دسترس‌پذیر backchannel همان منبع، کلاینت و لاگ‌ها را بررسی کنید؛ درخواست بعدی اعتبار بالادستی را دوباره می‌سنجد. |
| ورود به پورت دیگری منتقل می‌شود | issuer، hostname، callback، `APP_URL` و تنظیمات Nginx را با جدول آدرس‌ها تطبیق دهید. |
| خطای کلید رمزنگاری یا کوکی | کلیدهای `APP_KEY` و `NUXT_AUTH_COOKIE_KEY` را با تنظیمات خصوصی همان محیط تطبیق دهید؛ کلید جدید را جایگزین تصادفی دادهٔ موجود نکنید. |

حذف کامل دادهٔ توسعه فقط با فرمان صریح زیر ممکن است و تمام volumeهای پروژه را پاک می‌کند:

```bash
./scripts/dev reset --delete-development-data
```

این فرمان برای ارتقا، ایمپورت یا راه‌اندازی روزمره لازم نیست.


## تکمیل فاز دوم

ایمپورت User جدید به ناحیه اولیه صریح نیاز دارد؛ `AREA_ID` را با شناسه ناحیه واقعی جایگزین کنید. آماده‌سازی محل کاربران موجود، قرارداد اجباری‌شدن ناحیه و مدیریت اولیه دسترسی در [راهنمای شرکت و پرسنل](organization.fa.md) آمده است. `migrate` معمولی جایگزین اجرای صریح `organization:require-locations` پس از آماده‌سازی کاربران موجود نیست.
