# راهنمای شرکت، پرسنل و دسترسی‌ها

این راهنما مربوط به فاز دوم تأییدشده در ۸ نوامبر ۲۰۲۶ است. برنامه از آدرس `http://localhost:8081` در دسترس است؛ پورت‌های مدیریت سرویس‌ها برای ورود عادی کاربران نیستند.

## استفاده از پنل

پس از ورود، «مدیریت سازمان» و پیشخوان فقط بخش‌های مجاز را نشان می‌دهند. گروه‌های ساختار سازمان، پرسنل و دسترسی‌ها شامل کارت‌های آیکون‌دار هستند. گروهی که هیچ صفحه مجازی ندارد نمایش داده نمی‌شود. در موبایل منوی همبرگری از سمت راست باز می‌شود. واردکردن مستقیم لینک بدون مجوز، صفحه ۴۰۳ را نمایش می‌دهد؛ داشتن لینک یا انتخاب شرکت به‌تنهایی مجوز ایجاد نمی‌کند.

در هدر، منوی حساب نام فرد و منبع ورود را نشان می‌دهد. حالت روشن، تاریک یا خودکار را از گروه دکمه‌ها انتخاب کنید. انتخاب فرد واردشده در حسابش ذخیره می‌شود و در رفرش و ورود بعدی اعمال می‌شود. حالت خودکار تغییرات تم دستگاه را دنبال می‌کند. اگر ذخیره انجام نشود، پیام خطا می‌بینید و انتخاب قبلی برمی‌گردد. برای خروج، گزینه خروج را بزنید و تأیید کنید؛ انصراف ورود شما را حفظ می‌کند.

مودال‌ها با کلیک روی فضای بیرون بسته نمی‌شوند. Escape مودال را می‌بندد؛ اگر فهرست انتخابی باز باشد، Escape اول فهرست و بار دوم مودال را می‌بندد. هنگام ارسال اطلاعات یا شروع انتقال ورود، بسته‌شدن موقتاً مسدود است. با انصراف یا Escape، تغییرات ذخیره‌نشده ثبت نمی‌شوند.

## ساختار سازمان و محل استقرار

۱. شرکت را ایجاد کنید؛ سپس در صفحه چارت و پوزیشن‌ها همان شرکت را انتخاب کنید.
۲. پوزیشن ریشه را بدون بالادست بسازید. برای زیرمجموعه، بالادست همان شرکت را انتخاب کنید. چرخه یا بالادست از شرکت دیگر پذیرفته نمی‌شود.
۳. عنوان پوزیشن و بالادست در جدول و گزینه‌های فرم با مسیر کامل «شرکت / ریشه / والدها / پوزیشن» نمایش داده می‌شود. در فرم، فقط نام خود پوزیشن را در عنوان بنویسید؛ پیش‌نمایش مسیر کامل با تغییر عنوان یا بالادست به‌روز می‌شود.
۴. در بخش ساختمان‌ها، هر ساختمان یک ناحیه پیش‌فرض «نامشخص» دارد. این ناحیه را جداگانه حذف یا تغییرنام ندهید. ناحیه‌های دیگر را در همان ساختمان تعریف کنید.
۵. هر فرد باید دقیقاً یک ناحیه استقرار داشته باشد؛ این محل به شرکت وابسته نیست. محل افراد را پیش از حذف ناحیه یا ساختمان جابه‌جا کنید. سیستم افراد را خودکار منتقل نمی‌کند.

پوزیشن دارای زیرمجموعه، فرد یا مدیر گزارش‌دهیِ ارجاع‌دهنده قابل حذف مستقیم نیست؛ ابتدا وابستگی را برطرف کنید. تبدیل پوزیشن ریشه اشغال‌شده به زیرمجموعه نیز ممکن است تا تعیین مدیران افراد رد شود.

## پرسنل، سمت‌ها و مدیران

پرسنل از حساب‌های ایمپورت‌شده می‌آیند؛ این پنل حساب و رمز محلی نمی‌سازد. ویرایش مشخصات یا محل مشترک فرد به مجوز سراسری نیاز دارد.

در «سمت‌ها و گزارش‌دهی»، شرکت و فرد و سمت را انتخاب کنید. فرد می‌تواند چند سمت در یک یا چند شرکت داشته باشد و یک سمت می‌تواند چند نفر داشته باشد. برای هر انتساب، مدیران را جدا انتخاب کنید؛ سمت‌های دارای بالادست حداقل یک مدیر لازم دارند و برای ریشه اختیاری است.

مدیر یک پوزیشن است، نه شخص. می‌تواند از شرکت دیگر، بدون فرد یا متفاوت با بالادست چارت باشد. همان پوزیشنِ انتساب نمی‌تواند مدیر خودش باشد. جدول و فرم‌ها مسیر کامل سمت و هر مدیر را نشان می‌دهند. ویرایش انتساب، مدیران را جایگزین می‌کند؛ برای تغییر فرد یا سمت باید انتساب مربوط را حذف و انتساب مناسب ایجاد کنید. اطلاعات فقط وضعیت فعلی است و سابقه استخدامی نگهداری نمی‌شود.

## نقش و مجوز

نقش‌ها و مجوزهایشان بین شرکت‌ها مشترک‌اند. ابتدا نقش و مجموعه مجوزهای آن را تعریف کنید؛ سپس در «تخصیص دسترسی» کاربر یا پوزیشن را با نام و مسیر کامل انتخاب کنید.

- نقش سراسری در همه شرکت‌ها و مسیرهای سراسری معتبر است. نقش شرکتی فقط در همان شرکت معتبر است.
- می‌توان به فرد بدون سمت در شرکت هم نقش شرکتی داد.
- نقش پوزیشن به همه افراد فعلی همان پوزیشن می‌رسد؛ زیرمجموعه‌های چارت یا مدیران آن را به ارث نمی‌برند.
- مجوزهای مستقیم و ناشی از سمت با رعایت محدوده جمع می‌شوند. صرف داشتن سمت، مجوز ایجاد نمی‌کند.
- ذخیره فرم، مجموعه نقش‌های همان محدوده را جایگزین می‌کند. مدیر صرفاً شرکتی نمی‌تواند نقش سراسری را ببیند یا تغییر دهد.
- تخصیص‌دهنده باید خودش اختیار واگذاری همه مجوزهای نقش را داشته باشد. انتساب فرد به پوزیشن دارای نقش هم این بررسی را دارد.
- حذف آخرین مدیر مؤثر سراسری دسترسی‌ها مجاز نیست. تغییرات دسترسی در درخواست بعدی اثر می‌کند و به ورود مجدد نیاز ندارد.

## آماده‌سازی و ارتقای عملیاتی

فرمان‌ها از ریشه مخزن اجرا می‌شوند. برای محیط دارای داده، پیش از تغییر migration از داده نسخه پشتیبان بگیرید؛ از reset یا migrate:fresh برای ارتقا استفاده نکنید. مسیرهای خصوصی نگاشت باید داخل کانتینر قابل‌خواندن باشند.

```bash
docker compose exec -T backend php artisan migrate --force --no-interaction
docker compose exec -T backend php artisan organization:prepare-locations --building='توسعه' --dry-run
docker compose exec -T backend php artisan organization:prepare-locations --building='توسعه'
```

گزینه `--building` ساختمان و ناحیه نامشخص را آماده و کاربرانِ بدون محل را به همان ناحیه منتسب می‌کند؛ محل افراد دارای ناحیه تغییر نمی‌کند. اگر به‌جای انتخاب ساختمان می‌خواهید یک ناحیه موجود را تعیین کنید، از گزینه جایگزین زیر استفاده کنید؛ `AREA_ID` را با شناسه واقعی جایگزین کنید و `--building` و `--fallback-area` را هم‌زمان نفرستید:

```bash
docker compose exec -T backend php artisan organization:prepare-locations --fallback-area=AREA_ID --dry-run
docker compose exec -T backend php artisan organization:prepare-locations --fallback-area=AREA_ID
docker compose exec -T backend php artisan organization:require-locations
```

به‌جای fallback یکسان، گزینه `--mapping-file=/run/organization/user-area-map.json` با شیء JSON نگاشت شناسه کاربر به ناحیه نیز وجود دارد. قرارداد محل اجباری تا رفع کاربران بدون ناحیه معتبر اجرا نمی‌شود. در محیط بررسی این فاز، کاربر صریحاً ساختمان «توسعه» و ناحیه «نامشخص» را برای کاربران موجود انتخاب کرد؛ این تصمیم را برای محیط دیگری حدس نزنید.

ایمپورت کاربری که هنوز User ندارد به محل اولیه صریح نیاز دارد؛ کاربران موجود محل فعلی خود را حفظ می‌کنند:

```bash
docker compose exec -T backend php artisan login:import-members --source=primary --building-area=AREA_ID --dry-run
docker compose exec -T backend php artisan login:import-members --source=primary --building-area=AREA_ID
```

مجوزها از کد همگام می‌شوند؛ این فرمان نقش مدیر را آماده می‌کند اما به کسی نقش نمی‌دهد:

```bash
docker compose exec -T backend php artisan access:sync-permissions
```

فقط اپراتور مجاز، حساب موجود را با slug منبع و subject دقیق همان Member برای مدیریت اولیه انتخاب می‌کند. از نام/ایمیل برای تطبیق خودکار استفاده نکنید:

```bash
docker compose exec -T backend php artisan access:bootstrap --source=SOURCE_SLUG --subject=EXACT_SUBJECT --dry-run
docker compose exec -T backend php artisan access:bootstrap --source=SOURCE_SLUG --subject=EXACT_SUBJECT
```

در زمان اجرای اولیه فاز، کاربر تخصیص خودکار مدیر را نخواست؛ تأیید نهایی فاز مجوز تخصیص نقش جدید به حسابی نیست. نقش‌های موجود اپراتورها در روند آزمون تغییر داده نشدند.

## بررسی و رفع مشکل

```bash
docker compose exec -T backend php artisan test --compact
docker compose exec -T frontend npm run typecheck
docker compose exec -T frontend node --experimental-strip-types --test tests/admin-navigation.test.ts tests/appearance.test.ts
docker compose exec -T frontend npm run build
```

تست بک‌اند فقط روی دیتابیس ایزوله با پسوند `_test` اجرا می‌شود. پس از بیلد در محیط توسعه، سرویس frontend را دوباره راه‌اندازی کنید تا بررسی مرورگر با فایل‌های تولیدشده تداخل نداشته باشد. اسکریپت `smoke-management.py` فقط در پروژه موقت `organization-fresh-acceptance` اجرا می‌شود و برای محیط فعال نیست. آزمون‌های قطع سرویس/راه‌اندازی تازه را هنگام استفاده دیگران اجرا نکنید.

خطای ۴۰۳ را با مجوز همان عملیات و محدوده شرکت بررسی کنید؛ خطای ۴۰۹ معمولاً وابستگی، چرخه، مدیر الزامی یا حفاظت مدیر نهایی است؛ خطای ۴۲۲ به اطلاعات ورودی مربوط است. اگر بررسی هویت در دسترس نیست، سلامت منبع ورود را بررسی کنید و آن را با نداشتن مجوز یکی ندانید. قراردادهای دقیق در [مستندات API](../technical/management-api.md) آمده‌اند.
